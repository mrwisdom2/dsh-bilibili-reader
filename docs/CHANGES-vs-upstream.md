# 我们对上游插件做了什么（以及为什么）

**总原则：不改上游源码、不分发它的代码。**所有改动都由 `patch-plugin.sh` 在**运行时**施加 ——
它幂等（打过就跳过）、每次替换前先写 `.bak`，**上游升级后重跑一次即可**。

每个补丁回答三件事：**为什么 / 改了什么 / 上游修了吗**（核对时间：2026-10-25，上游 v2.0.4 / v2.1.0）。

---

## A. 七件运行时补丁（改的是插件的文件）

| # | 改哪里 | 为什么 | 上游修了吗 |
|---|---|---|---|
| **1** | `index.js`：删掉「私信里不要写"本鱼/本鲸/主人/人家"那套」 | 那句话是上游写死的**人设禁令**，与"自定义人设"直接冲突；我们换成许可版 | ❌ 2.0.4/2.1.0 里那句话还在（2.1.0 只是把**公开评论**默认改成中性、人设改可选）|
| **2** | `favops.py`：修自动收藏 | 上游调用了本机 `bilibili-api` 里**不存在**的类、还漏了 import ⇒ 这个功能**从来没成功过**；正确入口是 `Video.set_favorite(add_media_ids=[…])` | ⚠️ 上游换过写法，但仍是同一块逻辑 ⇒ **每次升级都要重新核对**（我们的补丁会报"结构不认识了"）|
| **3** | `asr.py`：加 `--max-minutes`（默认 30） | 长视频转写出来是废稿（中英混杂、整段重复），而且等不起；超限直接跳过并写明原因（返回码 3）| ❌ 仍在 |
| **4** | `meow-memory/lib/index.js`：7 处定时器 unref | 不谈这个插件本身，而是**我们另外装的记忆插件**：它的定时器没 unref ⇒ 一次性 headless 会话**永不退出** ⇒ 刷B站永久挂死（不报错、不写结束日志、名额白烧）| 与上游无关（是我们叠加的那层）|
| **5** | `lib/dm.mjs`：私信图片带出 URL | 否则主人发来的图在那一轮里显示成「[非文字消息]」，她**根本看不到** | ❌ 仍在 |
| **6** | `index.js`：私信提示词改成「正常回、别自己分条」 | 与 ⑦ 配套：**分条交给发送层**，模型自己分 ⇒ 双重切 | ❌ 仍在 |
| **7** | `mcp_server.py`：`bili_send_message` **发送层切条** | 去掉字数限制后，长回复会撞 B站 **单条 500 字硬限**（`code 21007`）直接发不出去 ⇒ 按 ~100 字切条连发（优先句末标点 → 逗号/空格 → 硬切），间隔 0.8s | ❌ 仍在（但 2.0.4 给这个函数加了「**没有 msg_key 回执就算没送到**」的检查 —— 我们移植时**保留**了它）|

> ⚠️ **补丁失配是常态**：⑤⑦ 这类"整块替换"的补丁，上游一改函数体就会失配。
> 正解不是手调锚点，而是**按新版本反推**：把新版的整块函数原样取出来当 `OLD`，把我们的改动移植成 `NEW`
> （`patches/dmsplit_patch.py` 就是这么重生成的）。

## B. 宿主侧增强（**完全不碰插件**，这是我们的主路线）

| 组件 | 干什么 |
|---|---|
| `dm-session.mjs`（包装器） | 插件只认一个「dsh 路径」配置 ⇒ 我们把 `dshBin` 指向它：**只在私信轮**插 `--session-id`（换来连续性）、给所有轮套 `caffeinate -i`（防空闲睡眠冻死）、追加视觉 MCP 的 `--patch` |
| `duty_mcp.py`（自建 MCP） | `view_image` 看图 / `bili_frames` 抽真帧 / `search_finds` 语义检索历史 / `have_seen` 判重。**为什么自己写**：上游的 MCP 白名单是硬编码的、每轮重写 overlay，塞不进去 ⇒ 正解是"别在插件里加能力，改在宿主侧代劳" |
| `feedback.py` | 采集三类反馈写进人设文件（见 `docs/DESIGN.md`）|
| `rag.py` | 把日报/笔记/归档/判重表做成**本机 RAG 索引** ⇒ 历史可检索、语义判重 |
| `selfcheck-headless.sh` | 每天确认：headless 那一轮**能自己退出**（防插件升级冲掉补丁④）+ 私信会话有没有被别的进程占着 |
| 每日九步任务 | 沉淀 / 台账 / 偏好 / 快照告警 / 失败轮次 / 基线自检 / 索引 / 归档 / 简报 |

## C. 为什么**不**跟上游 2.1.0 的「最小权限 profile」路线

2.1.0 做了一件很对的事：给值班轮换成专用 profile，关掉
`tool-fs` / `tool-bash` / `tool-web` / subagent / workflow / skill / **`agent-instructions`** /
plugin-manager / hmr / …，并把"写日报、写判重表"改成**固定路径的窄口 MCP 工具** ——
**从架构上关掉了「读到 → 发出去」这条链**。这是质的安全提升。

**但代价与我们这条路线正面冲突**：

- 关掉 `agent-instructions` + 那一轮**没有文件工具** ⇒ 我们「人设/反馈台账写在 `AGENTS.md`、
  让模型自己读」的整套设计**失效**（`~/.agents/AGENTS.md` 不再加载，她也读不到文件）。
  要迁移就得把人设塞进 `personaPrompt`（2.1.0 把上限提到 4 万字，够用）、并给反馈台账另找投递方式。
- 上/下游的 `mcp_server.py` 在 2.0.4→2.1.0 之间**差了 432 行** ⇒ 补丁⑦要重写。
- 原生 `bili_cover` / `bili_frames` 是**从 B站 故事板裁 480×270 小图**，不如我们自建的
  （yt-dlp + ffmpeg 抽**真帧**）。

**所以我们停在 2.0.4**（它已经拿到 4 个安全修复：主人身份只认真填 UID / 不把提示词交给 shell /
overlay 路径按 YAML 转义 / 控制接口只接受本机同源请求；**并删掉了四个高危工具**：上传视频、
发动态、发专栏…）。

**我们知道留下的取舍**：值班轮仍然是一个"能读全盘"的进程 ⇒
**红线只能靠章程与人设守**（这是我们的红线条目，也是本仓库最需要注意的地方）。
想关掉它，就得走 2.1.0 那条迁移 —— 那是一件独立的事，不是顺手升级。
